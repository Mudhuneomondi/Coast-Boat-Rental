Mid-semester assessment against the **[OWASP Top 10 (2025)](https://top10.owasp.org/2025/)**. Backend: Supabase (PostgreSQL + Auth + Storage).

## 1. Supabase Auth (A07, A04)

**Before:** passwords were stored in plain text (`password_hash = 'demo123'`) and compared in the browser; staff were recognised by an `@coastboat.com` e-mail; the role lived in a JS variable.

**Now**
- Sign-up / sign-in use `supabase.auth.signUp / signInWithPassword`. Supabase hashes passwords (bcrypt), rate-limits attempts, issues short-lived JWTs and refreshes them. The `password_hash` columns are **dropped**.
- Password policy: ≥ 10 characters with letters and numbers (client) — plus the dashboard settings below.
- Same message for "unknown user" and "wrong password" → no account enumeration. Sign-up gives the same reply whether or not the e-mail exists.
- **Who is staff is decided by the server.** After login the app calls `bootstrap_profile()`; staff exist only if an Admin created a row in `staff_invites` and that person confirmed the e-mail. `user_metadata` (which users can edit) is never used for roles — tested.
- Soft-deleted accounts are locked out at the next login; they are not silently re-created as customers.
- Auto sign-out after 15 min of inactivity; logout wipes rendered data from the DOM.

## 2. Row Level Security (A01)

RLS is **enabled on all 8 tables**; the old `DISABLE ROW LEVEL SECURITY` lines are gone and any leftover policy is dropped on every run.

| Table | Customer | Operator | Manager | Admin |
|---|---|---|---|---|
| boats | read | read | read / add / change status / archive | + see archived |
| customers | read/update **own** row (name, phone, ID) | read | read | + archive |
| bookings | create & read **own**, cancel own *Pending* | read, create | read, approve / reject / complete | + see archived |
| payments | read **own** | — | read | read |
| incidents | — | read, report | + resolve | + archive |
| users, staff_invites | — | — | — | all |
| audit_log | — | — | — | read-only |

Defence in depth beyond policies: `anon` has **no** privileges at all; `authenticated` gets **column-level** grants only (e.g. a customer cannot even send `total_amount`, `status`, `payment_status`, `role` or `deleted_at`); `DELETE` is granted on nothing but `staff_invites`; helper functions are `SECURITY DEFINER` with a pinned `search_path`. Storage: `boats` bucket (public photos, managers upload), `incidents` bucket **private** (staff only, signed URLs), 2–3 MB limit, JPG/PNG/WebP only, server-checked file names.

## 3. XSS clean-up (A05)

- Every database value placed in `innerHTML` goes through `esc()` (escapes `& < > " ' \``); numbers through `int()`; badge classes come from an allow-list.
- **No inline event handlers anywhere** (44 removed from `index.html`, all in templates). Buttons use `data-click="name"` + one delegated listener that only runs functions registered in an allow-list.
- Image URLs only render if they point at our own Supabase origin; anything else (`javascript:`, foreign hosts) becomes a local placeholder. Photos are checked by size, MIME and **magic bytes** and stored under random UUID names.
- Toasts use `textContent`. The old `alert()` error popups that leaked file names and stack info are gone.
- Verified with a real Chromium: `<img onerror>` and `<script>` payloads placed in names, notes, references, audit fields etc. show up as literal text on every screen, `window.__pwned` stays undefined.

## 4. Booking price & double-booking (A06)

Enforced **in the database**, so a modified browser or a direct API call cannot bypass it (`trg_booking_before_insert`, `bookings_no_overlap`):
- Price = nights × the boat's current `base_price`, computed by the server. The client no longer sends price, status or payment status (and is not permitted to).
- Start date not in the past (Nairobi time), end after start, max 30 days, boat must exist and not be in Maintenance, customers can only book for themselves.
- **No double-booking:** an exclusion constraint forbids two *Approved* bookings overlapping on one boat (`[start, end)` — checkout day can be the next check-in). New requests that overlap an approved booking are rejected immediately; two overlapping *pending* requests can exist but the second cannot be approved.
- Status workflow enforced by trigger (e.g. only Pending→Approved/Rejected/Cancelled by managers; a customer may only cancel their own Pending request; *Completed* requires *Paid*). `approved_by` is stamped by the server.
- CHECK constraints on lengths, ranges, enumerations, e-mail/phone formats on every table.

## 5. Audit log, triggers, soft deletes (A09)

- `audit_log` records table, row id, action (INSERT / UPDATE / SOFT_DELETE / RESTORE / DELETE), changed fields, old and new values, and **who** (JWT user id, e-mail, role) — written by triggers on 7 tables, so it cannot be skipped by the app.
- The log is **append-only** (trigger blocks UPDATE/DELETE even for the DB owner) and Admin-read-only. Admin screen: *Audit Log*.
- **Soft deletes:** `deleted_at` / `deleted_by` on users, boats, customers, bookings, incidents. Only the `archive_record()` function can set them (clients have no column privilege), stamps are set by the server, rows vanish from normal views, an Admin can restore. Hard `DELETE` is impossible (no privilege + trigger).
- Payments are immutable (no update/delete for anyone).
- You cannot remove or demote yourself (no lock-out).

## 6. CSP & security headers (A02)

`index.html` carries a CSP meta tag (works on any static host); `_headers` (Netlify / Cloudflare Pages) and `vercel.json` carry the same policy **plus** the header-only protections. They are generated from the meta tag by `npm run build`, and CI fails if they differ.

```
default-src 'none'; script-src 'self'; style-src 'self'; style-src-attr 'unsafe-inline';
img-src 'self' data: blob: https://<project>.supabase.co; font-src 'self';
connect-src 'self' https://<project>.supabase.co wss://<project>.supabase.co;
object-src 'none'; base-uri 'none'; form-action 'self'; upgrade-insecure-requests
(+ header only) frame-ancestors 'none'
```
Plus `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `Strict-Transport-Security`, `Cross-Origin-Opener-Policy`.
No inline scripts, no `eval`, no third-party hosts — possible because Tailwind is compiled ahead of time and inline handlers were removed.

## 7. Libraries, SRI, npm, Dependabot (A03, A08)

- Runtime CDNs (`cdn.tailwindcss.com`, unpinned `chart.js`, `supabase-js@2`) are **gone**. `package.json` pins exact versions (`.npmrc`: `save-exact`, `ignore-scripts`), `package-lock.json` pins the whole tree with integrity hashes.
- `npm run build` copies the libraries into `vendor/`, compiles Tailwind and writes a **sha384 `integrity` hash** onto every `<script>`/`<link>` in `index.html`. `npm run verify` fails if any file and hash disagree.
- `npm audit`: **0 vulnerabilities** (Tailwind 4.3.0 chosen because v3's CLI depended on the vulnerable `braces`).
- `.github/dependabot.yml`: weekly PRs for npm and GitHub Actions. `.github/workflows/ci.yml`: `npm ci`, `npm audit`, build + verify, and runs the database security tests on PostgreSQL 16.

## 8. Atomic payments & error handling (A10, A06, A09)

- **Payments:** clients cannot insert into `payments`. They call `record_payment()` — one transaction that locks the booking row, validates (approved booking, amount > 0, not above the balance, method list, M-Pesa code format), inserts the payment and updates `payment_status`. Any failure rolls back everything; concurrent payments queue on the row lock; a unique index on (method, reference) stops duplicate M-Pesa codes; the UI also blocks double-clicks.
- **Errors:** `friendlyError()` maps database codes to plain messages (double booking, duplicate, permission…). Raw SQL errors, table names and stack traces stay in the console only. Global handlers log instead of `alert()`. Debug `console.log`s that printed e-mails and password lengths were removed. The "disable RLS to fix this" hint is gone.

## One-time set-up (Supabase dashboard — cannot be done from code)

1. **SQL Editor →** paste & run `schema.sql` (safe to re-run). Optional: `supabase/seed.sql` for demo boats.
2. **First admin:** run `insert into public.staff_invites (email, full_name, role) values ('you@example.com','Your Name','Admin');` then sign up in the app with that e-mail, confirm it, sign in. Invite everyone else from *Users → Invite Staff*.
3. **Authentication → Providers → Email:** keep **Confirm email = ON** (staff promotion requires a confirmed address); set **minimum password length 10**, require letters + digits; enable *leaked password protection* if your plan has it.
4. **Authentication → URL Configuration:** set *Site URL* and add your deployed URL to *Redirect URLs*.
5. **Authentication → Rate limits / CAPTCHA:** leave defaults on; enable CAPTCHA if the site is public.
6. Old demo staff rows (`admin@coastboat.com` … `demo123`) are retired automatically; delete the old Auth/Storage test data you no longer need.
7. `npm install && npm run build` after changing any file under `js/` or `css/` (SRI hashes) — CI checks it.

## Honest limitations (what a real deployment would still need)

- Customer payments are **self-reported** (as in the original design). A real M-Pesa flow must confirm the transaction server-side (Daraja callback in an Edge Function) before marking money received.
- No MFA for staff; customer ID numbers are stored in clear text (consider column encryption).
- On hosts that cannot send headers (e.g. GitHub Pages) the CSP meta tag applies, but `frame-ancestors`, HSTS and the other header-only protections do not.
- `style-src-attr 'unsafe-inline'` remains because templates use a few `style=""` attributes (cannot execute script).
